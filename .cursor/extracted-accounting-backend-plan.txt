INSIGHTBOOKS V2
Full Accounting Backend Reimplementation Plan
Product: InsightBooks Business Management System Primary Objective: Rebuild the entire accounting backend so that every financial transaction is posted once, posted to the correct accounts, fully traceable, and consistently reflected in the General Ledger, Trial Balance, financial statements, operational reports, bank reconciliation, equity reports, accounting periods, and financial projections.
1. IMPLEMENTATION VISION
InsightBooks must be transformed from a collection of financial modules into a unified financial operating system.
The system currently contains accounting inconsistencies including:
· Unbalanced Trial Balance results. · General Ledger balances that do not agree with reports. · Duplicate financial postings. · Transactions posted to incorrect accounts. · Parent and child accounts being counted together incorrectly. · Owner capital appearing more than once. · Liabilities appearing in the Chart of Accounts but not in journals. · Reports reading directly from operational tables. · Different modules calculating their own independent balances. · Missing or incomplete transaction audit trails. · Posted transactions being editable without proper reversals. · Financial reports that cannot be traced to their source transactions.
The reimplementation must establish one authoritative accounting path:
Operational Transaction 
Accounting Posting Engine 
Balanced Journal Entry 
Journal Entry Lines 
General Ledger 
Trial Balance 
Financial Statements

 Management Reports and Forecasts
Every financial module must use this same path.
The General Ledger must become the single source of truth for financial reporting. Operational modules such as sales, purchases, payroll, inventory, expenses, banking, loans, fixed assets, and equity must never update financial reports or account balances directly.
2. PROJECT OBJECTIVES
The implementation must accomplish the following objectives:
2.1 Accounting Integrity
· Every posted journal entry must balance. · Total debits must always equal total credits. · Every business transaction must create no more than one accounting event. · Duplicate posting must be prevented at database and application levels. · Every posting must use the correct Chart of Accounts mappings. · Parent and child accounts must not be double-counted. · Posted entries must become immutable. · Corrections must be performed through reversals or adjustment journals.
2.2 Reporting Integrity
· The Trial Balance must be generated exclusively from posted journal lines. · The General Ledger must be generated exclusively from posted journal lines. · The Balance Sheet must be generated exclusively from the General Ledger. · The Income Statement must be generated exclusively from the General Ledger. · Cash Flow, equity, tax, aging, inventory, payroll, and management reports must reconcile with
the General Ledger. · Every report figure must show the account code and account name from which it was derived. · Every figure must support drill-down to journal lines and source transactions.
2.3 Data Preservation
· Existing production data must not be deleted. · Database migrations must be additive and reversible. · Historical transactions must be analyzed before modification. · Data repair scripts must be idempotent and safe to rerun. · Every repair must be logged. · A full backup and rollback strategy must be created before any production migration.

3. IMPLEMENTATION PRINCIPLES
The development team must follow these principles throughout the project.
3.1 General Ledger as the Single Source of Truth
Financial statements must never calculate balances directly from:
· Invoice tables · Payment tables · Sales tables · Expense tables · Inventory tables · Payroll tables · Asset tables · Bank transaction tables · Loan tables · Equity transaction tables These operational tables may provide supporting information, but financial values must come from posted journal entries.
3.2 One Accounting Event, One Posting
Each financial event must have a unique accounting identity.
Examples:
Invoice ID + POST_INVOICE Payment ID + POST_CUSTOMER_PAYMENT Expense ID + POST_EXPENSE Payroll Run ID + POST_PAYROLL Asset ID + POST_ASSET_ACQUISITION
The system must reject attempts to post the same event more than once.
3.3 Balanced Entries
Before posting:
Sum of Debits = Sum of Credits
Any unbalanced entry must be rejected before the database transaction is committed.
4

3.4 Atomic Posting
The following actions must occur inside one database transaction:
1. Validate the source transaction. 2. Resolve account mappings. 3. Create the journal entry. 4. Create journal lines. 5. Mark the source transaction as posted. 6. Create audit records. 7. Update any rebuildable reporting projections or caches. 8. Commit everything together. If any step fails, the entire transaction must roll back.
3.5 Immutability
Once posted:
· Journal dates cannot be silently changed. · Accounts cannot be changed. · Debit and credit values cannot be edited. · Journal lines cannot be deleted. · Source linkage cannot be changed. · Posted source transactions cannot be financially edited. Corrections must use:
· Full reversal · Partial reversal where legally and structurally appropriate · Adjustment journal · Credit note · Debit note · Void-and-repost workflow
3.6 Exact Monetary Values
All monetary values must use exact decimal database types.
Do not use:
· JavaScript floating-point calculations for accounting totals. · Database FLOAT or REAL types for financial amounts. · Rounded intermediate values without defined precision rules. Use controlled decimal precision and currency rounding policies.
3.7 Separation of Actuals and Forecasts
Actual accounting data and financial projections must remain separate.
5

Actual Data  General Ledger
Forecast Data  Projection Models
Forecasts must never post to the actual General Ledger.
4. PROJECT DELIVERY STRATEGY
The system must not be rewritten in one uncontrolled release.
Implementation must be divided into controlled phases.
Each phase must include:
· Repository analysis. · Database analysis. · Technical design. · Implementation. · Automated testing. · Data validation. · User acceptance testing. · Migration scripts. · Rollback scripts. · Technical documentation. · Deployment checklist. · Sign-off criteria.
The recommended implementation order is:
Phase 0 -- Project Safety and Environment Preparation Phase 1 -- Complete Accounting Forensic Audit Phase 2 -- Target Accounting Architecture Phase 3 -- Chart of Accounts Reconstruction Phase 4 -- Accounting Posting Engine Phase 5 -- Journal and General Ledger Reimplementation Phase 6 -- Historical Data Reconciliation and Repair Phase 7 -- Trial Balance and Financial Reports Phase 8 -- Financial Calendar and Accounting Periods Phase 9 -- Operational Module Integration Phase 10 -- Bank Reconciliation Phase 11 -- Equity Management Phase 12 -- Period Closing and Year-End Closing Phase 13 -- Financial Planning and Projection Phase 14 -- Loan Readiness and Executive Reporting Phase 15 -- Security, Audit, and Compliance Phase 16 -- Performance and Scalability
